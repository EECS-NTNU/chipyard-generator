# Chipyard Generator

The sbt plugin resolves a hardware workspace from its `build.sbt`. It fetches pinned Git sources, fingerprints local source directories, and records one dependency graph for the workspace. A pinned Chipyard recipe compiles and elaborates a selected experiment from the workspace root.

## Develop Chipyard Generator in VS Code

Open this checkout with VS Code and run **Dev Containers: Reopen in Container**. The [development config](.devcontainer/devcontainer.json) mounts the checkout for editing and provides JDK 17, sbt, Git, and Scala Metals. Run `bash cli/setup.sh` inside the container if you want to set up `presolve` and configure a Chipyard toolchain.

Docker uses the default backend. On the cluster, connect using Remote SSH and set `dev.containers.dockerPath` in the remote VS Code settings to the absolute path of [`containers/podman`](containers/podman) in this checkout. The wrapper uses node-local temporary storage and Podman's `keep-id` mapping so VS Code can write to the mounted checkout. Podman's image storage also belongs on node-local storage when your home directory is on Lustre. [VS Code backend settings](https://code.visualstudio.com/remote/advancedcontainers/docker-options#podman) · [Podman UID mapping](https://docs.podman.io/en/stable/markdown/podman-run.1.html#userns-mode) · [Podman storage](https://docs.podman.io/en/stable/markdown/podman.1.html#note-unsupported-file-systems-in-rootless-mode)

## Run a project with the container image

Build the runtime image on Linux x86-64 from the generator checkout. Use `podman` for the cluster or `docker` on a Docker host. The image packages `presolve`, the sbt plugin, and the pinned Chipyard toolchain. The image build downloads and installs the toolchain.

```bash
engine=podman
TMPDIR=/tmp "$engine" build -t presolve-runtime .
```

In Bash, set `project` to the absolute path of your source project. Edit that directory on the host and rerun the desired command. The project mount holds `hardware.lock` and generated outputs, and a separate mount retains downloaded sources and dependencies. The image filesystem is read-only.

```bash
project=/absolute/path/to/my-accelerator
cache="${XDG_CACHE_HOME:-$HOME/.cache}/presolve-container"
mkdir -p "$cache"

run_options=(--rm --read-only --tmpfs /tmp:exec,mode=1777 --user "$(id -u):$(id -g)")
if [[ $engine == podman ]]; then
  run_options+=(--userns=keep-id)
fi

presolve_container() {
  "$engine" run "${run_options[@]}" \
    --mount "type=bind,source=$project,target=/workspace" \
    --mount "type=bind,source=$cache,target=/cache" \
    presolve-runtime "$@"
}

presolve_container resolve
presolve_container compile baseline
presolve_container run baseline ./program.elf
```

To scaffold a project with the image, set `project` to an existing parent directory and run `presolve_container create-project my-accelerator`. Then set `project` to the new project directory for the build commands.

## Create a workspace with presolve

Run the guided setup from the Chipyard Generator checkout.

```sh
bash cli/setup.sh
source cli/target/presolve-env.sh
```

Setup checks Git, JDK 11+, and sbt, publishes the plugin locally, and prepares the launcher. You can use an existing Chipyard toolchain, install one with Conda on Linux x86-64, or configure it later. The installer downloads the pinned upstream checkout and puts its Conda environment under the checkout directory you select. Setup also offers to create and resolve a first workspace.

For manual setup, run the sbt tasks directly.

```sh
sbt publishLocal cli/stage
export PATH="$PWD/cli/target/stage:$PATH"
```

Keep the staged launcher and its `lib/` directory together if you move the installation. From a directory outside the checkout, create a workspace and resolve its dependencies.

```sh
presolve create-project my-accelerator
cd my-accelerator
presolve experiments
presolve resolve
presolve verify
```

The scaffold includes a starter Chisel module and a stock Rocket experiment named `baseline`. Commit the `hardware.lock` generated by `resolve`. After setting `CHIPYARD_TOOLCHAIN_PREFIX` as described in the [reference build](reference/chipyard-rocket/README.md), elaborate the baseline or simulate it with a RISC-V ELF. Chipyard's Make flow requires build, toolchain, and cache paths without spaces or shell metacharacters.

```sh
presolve compile baseline
presolve run baseline ./program.elf
```

`elaborate` and `simulate` are aliases for `compile` and `run`. Workspace commands also work from subdirectories. Relative ELF paths are resolved from the directory where you invoke presolve. Run `presolve --help` for the command list.

## Try it locally

With Git, a JDK (11 or newer), and sbt installed, publish the plugin and resolver to your local Ivy repository.

```sh
sbt publishLocal
sbt 'resolver/Test/runMain chipyard.generator.MilestoneOneChecks'
```

Copy the two fixture workspaces outside the tool checkout. Each pins the same locally published plugin version.

```sh
workspaces=$(mktemp -d)
cp -R fixtures/local fixtures/git "$workspaces/"
(cd "$workspaces/local" && sbt hardwareResolve hardwareResolve hardwareVerify)
(cd "$workspaces/git" && ./prepare.sh && sbt hardwareResolve hardwareResolve hardwareVerify)
(cd "$workspaces/git" && sbt 'set hardwareOffline := true' hardwareVerify)
```

Each workspace writes `hardware.lock` and a generated `target/hardware/<fingerprint>/plan.json`. The plan includes the checkout directories and dependency edges. `hardwareVerify` uses the same declarations and reports drift without rewriting the lock. Run `hardwareResolve` again to accept intentional changes to a declaration or local source.

## Workspace declarations

Add `addSbtPlugin("org.eecs-ntnu" % "sbt-chipyard-generator" % "0.1.0-SNAPSHOT")` to `project/plugins.sbt` and enable `ChipyardPlugin` in the workspace root's `build.sbt`.

```scala
enablePlugins(ChipyardPlugin)

chipyardVersion := "a7946ede9bd625204435715dc40c750e2f8a251f"

hardwareDependencies := Seq(
  Generator.chipyard("boom"),
  Generator.local("custom-cache", baseDirectory.value / "cache-generator")
)
```

Leave `chipyardVersion` unset for a platform-independent workspace. The bundled Chipyard recipe records the upstream toolchain configuration and the submodule checkouts needed by the stock build. After upgrading from the resolution-only recipe, run `sbt hardwareResolve` to record the additional platform pins.

Use `Generator.git(name, url, ref, alias = "...")` for an independent Git dependency. Supply a full 40-character commit ID. An alias identifies a graph node and defaults to the generator name. Use distinct aliases to resolve different revisions. For an independent source with explicit dependency requirements, use `Generator.git(...).requires(otherGenerator)`. A diamond shares a single node when both paths request the same dependency identity and edges.

Git sources default to `$XDG_CACHE_HOME/hardware-generators` or `~/.cache/hardware-generators`. Override the location with `hardwareCacheDirectory`. Set `hardwareOffline := true` to require prefetched Git sources. The cache publishes source trees by repository and commit. For a direct Git dependency, nested submodule checkouts are stored as separate entries and their locations appear in the plan. A Chipyard workspace fetches the platform tree and the generator repositories selected by its recipe.

Local source fingerprints include file contents and executable bits. The resolver skips Git metadata, standard sbt output directories at the source root and under `project/`, and the source root's `hardware.lock`. Symbolic links must resolve to included inputs inside the same local source directory.

## Elaborate and simulate

Use the toolchain prefix from the [M0 reference build](reference/chipyard-rocket/README.md). Set `CHIPYARD_TOOLCHAIN_PREFIX` or the sbt setting `hardwareChipyardToolchain` to that directory. In a Chipyard workspace, place a top-level class named `System` extending Chipyard `Config` in `config/<experiment>/System.scala` under a named Scala package. The generated build compiles that experiment directory, the workspace's `src/main`, ordinary source dependencies, and the generator aliases and optional integrations activated for the build.

```sh
sbt hardwareResolve
sbt 'hardwareElaborate baseline'
sbt "hardwareSimulate baseline \"$PAYLOAD\""
```

`PAYLOAD` is the path to a RISC-V ELF such as the one built by the M0 reference runner. The tasks verify the existing lock and print a fresh build directory under `target/hardware/builds/`. It contains the generated sbt build, RTL under `chipyard/sims/verilator/generated-src/`, and a `run.json` with the experiment, fingerprints, toolchain and payload identity. Generated directories are disposable. On clusters with a shared file-count quota, run from node-local scratch or set sbt's `target` to a separate scratch directory for each workspace.

The source project recipe uses each dependency's `src/main` with the pinned platform's Scala and Chisel settings. Use `.requires(...)` for explicit project edges. The generated build supplies its own sbt definitions for these source projects.

To compare revisions, declare each revision with a distinct alias that is a Scala package identifier. In each experiment, import a named package or symbol from the desired alias, such as `import boom_baseline.v3.common.WithNSmallBooms`. The generator must own a single top-level Scala package. The build replaces that package with the alias in its generated Scala sources and records the mapping and Git revision in `run.json`. A named import activates the revision and its declared dependencies. Each experiment can select one revision of a given generator. All experiments share the resolved graph, lockfile and cached source checkouts.

The two build fixtures include observables named `LocalCounter` and `GitCounter` in their respective generated RTL. The local fixture also includes the stock baseline experiment.

```sh
workspaces=$(mktemp -d)
cp -R fixtures/build-local fixtures/build-git "$workspaces/"
(cd "$workspaces/build-local" && sbt hardwareResolve 'hardwareElaborate counter')
(cd "$workspaces/build-git" && ./prepare.sh && sbt hardwareResolve 'hardwareElaborate counter')
```

## Standalone modules and optional integrations

For standalone elaboration, define one `src/main/scala/**/Module.scala` with a public top-level `object Module` in a named Scala package. Give it a `create()` call that constructs a fresh Chisel module. A factory such as `def create(params: CounterParams = CounterParams()): SelectedCounter` preserves typed parameters and supplies the default configuration. The task uses the pinned Chipyard toolchain and writes CIRCT's SystemVerilog under `rtl/` in the generated run directory. [Example parameterized module](fixtures/select/src/main/scala/selectfixture/Module.scala)

```sh
sbt hardwareResolve hardwareElaborateStandalone
# With the presolve launcher installed
presolve standalone
```

Put an optional integration's sources in `integrations/<unit>/src/main/scala` and its resources in `integrations/<unit>/src/main/resources`. The integration package starts with the owning `Module.scala` package followed by `.integrations.<unit>`. For example, `import myworkspace.integrations.uart.Adapter` selects the unit `integrations/uart`. The convention also applies to source projects in the resolved graph.

Qualified named imports, grouped imports, and renamed symbols can select units. The selector follows imports in ordinary sources, the selected experiment's helpers, and newly selected units. A wildcard alone cannot select an optional integration. The run's `sourceSelection` section lists the active Scala source files and the import location for each selected unit. Each experiment uses the same `hardware.lock`, and its sources and compiled classes live in its own generated build.
