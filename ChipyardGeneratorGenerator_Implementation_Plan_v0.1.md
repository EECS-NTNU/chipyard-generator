# Presolve (ChipyardGeneratorGenerator) implementation plan

**Companion to design v0.12 · Plan v0.2 · 27 November 2026**

The first delivery is a released tool that two independent hardware workspaces can use. A researcher pins the plugin, declares generators in `build.sbt`, and builds from the workspace root. Chipyard is a pinned platform dependency. The initial containerized build path reuses an existing Dockerfile/image that already installs a complete Chipyard distribution, rather than requiring a Presolve-specific toolchain image. The BTB exercises one capability, internal component replacement. A small whole-generator example exercises the same tool through a different integration path.

The decisions below are implementation defaults for the first prototype. The milestones describe evidence to collect. This plan records required evidence, not implementation status. Container integration, platform compatibility, host hooks and multi-version compilation must be qualified against the relevant exit tests.

## Architectural decisions

| ID | Decision | Consequence for implementation |
|---|---|---|
| A1 | Release the plugin, resolver, workspace generator and Chipyard recipes from the tool repository. Keep hardware, experiment definitions, dependency declarations and the lockfile in the user's workspace. | Test workspaces consume a published or locally packaged plugin by version. They can live as fixtures during development, but must also build after being copied outside the tool checkout. The generated build directory is disposable. |
| A2 | Use an sbt plugin as the initial front end. Let sbt evaluate the workspace's settings. Implement resolution and build-plan generation as Scala code callable independently of an sbt session. | The first command is `sbt hardwareResolve`. A later CLI can call the same operations. There is one user-authored dependency declaration surface. |
| A3 | Start with two build loads. The outer build resolves and writes a plan. A separate, generated sbt build compiles the resolved projects and selected sources. | This puts dependency discovery before construction of the compilation graph. The generated build uses the pinned Chipyard recipe and cannot recursively invoke the outer resolve task. Revisit native sbt project references only if they preserve this boundary and simplify the implementation. |
| A4 | Resolve once per workspace. Represent each generator instance by its declared identity, optional alias, resolved source and explicit dependency edges. | Preserve distinct revisions and share compatible platform nodes. Validate alias uniqueness and report both dependency paths on a platform conflict. An experiment selects from this graph. |
| A5 | Use a schema-versioned, deterministically ordered `hardware.lock`. Record roots, nodes, edges, revisions, submodule pins, recipes, toolchain and local source identities. | First resolve writes the lock. An ordinary build verifies it and reports drift. An explicit resolve updates it after a declaration or local dependency changes. Record workspace-relative local paths where possible and fingerprint their build inputs. Keep the experiment choice and run parameters in a separate run manifest. |
| A6 | Cache fetched sources by canonical repository and commit. Generate build files under the workspace's `target/hardware/`. | Publish complete cache entries atomically. Concurrent jobs use isolated writable build directories. Fingerprint compiled artifacts with the actual toolchain, recipes, dependency edges, selected sources and any alias transformation. |
| A7 | Use one Chipyard `Config` entry per selected `config/<experiment>/System.scala` for the first system build. Prototype a workspace-package convention with a class named `System`. | The build manager explicitly selects the experiment directory and passes its qualified entry class to elaboration. A baseline can omit the local hardware. Test the convention before publishing it as an API. |
| A8 | Start standalone support with one public `object Module` in the canonical `Module.scala`, a typed `create(params)` factory and workspace-supplied default parameters. | Generate a small compile-time-checked driver for a directly elaboratable Chisel module. Each call constructs fresh hardware. Validate the package/symbol convention with a second workspace before fixing the public signature. Diplomacy and external RTL may require different construction contexts. |
| A9 | Select optional integrations from named Scala imports before compilation. Resolve dependency aliases independently of this source-selection step. | Index exported integration packages or symbols by source unit. Traverse imports in active sources, including helpers and newly selected units, to a fixed point. Only resolved dependencies are eligible. Expose selected units and reasons in the build plan. |
| A10 | Keep platform- and host-specific knowledge in versioned recipes and adapters. The core tool handles source identities, build inputs, compilation and backend invocation. | A recipe identifies source/resource roots, compiler settings, project edges and required build steps. A workspace explicitly opts into an external build recipe before its commands run. A host-specific adapter owns the semantics of a replacement. |
| A11 | Adopt a complete, preinstalled Chipyard distribution as an optional platform provider. The initial container path runs the outer Presolve sbt plugin and the generated inner build inside the existing image. | Reuse the existing Dockerfile or published image; no Presolve-specific image layer is required when the plugin can be resolved normally. Discover or explicitly configure the installation root and initialization script. Preserve the installed checkout and toolchain. Native execution remains supported. |
| A12 | Treat installed source trees and compiled artifacts as candidates, not as the dependency graph. | Verify the installed platform commit, generator/submodule revisions and source integrity against the workspace's resolved graph. Reuse exact matches only. Local and explicitly pinned Git sources remain authoritative for their declared identities. Never silently fall back to baked-in hardware, compile both copies or add undeclared generators to the classpath. Fetch missing compatible sources; reject incompatible platform/toolchain combinations with actionable diagnostics. |
| A13 | Separate build backends from command execution environments. | A backend/recipe describes commands and required inputs; an execution runner handles commands, working directory, environment, mounts, outputs, cancellation and exit status. Initially use a native process runner inside the existing container; add Docker and Apptainer launch support without embedding container logic in the dependency resolver. Do not require nested Docker or a Docker socket. |
| A14 | Generate an isolated writable build workspace under `target/hardware/` (per run where needed). | Reuse installed scripts, libraries and matching sources without writing to the installed Chipyard tree. Materialize or reference inputs through a recipe; preserve paths and resources required by upstream tools. Start with ordinary mounts and, where necessary, copies. Copy-on-write overlays and more aggressive cache reuse are optimizations, not requirements. Keep user-owned hardware sources outside cleanup scope. |
| A15 | Extend the existing lock, build fingerprint and run manifest with execution provenance. | Lock the platform and toolchain identity including the immutable OCI image digest (and selected architecture/platform where applicable). Record the actual runtime, image/SIF checksum, resolved source identities, recipe, relevant environment settings and commands in the run manifest. Distinguish runtime-specific paths from portable dependency identities; do not accept a mutable tag or a Dockerfile hash alone as proof of image identity. |

## Milestones and exit tests

| Milestone | Implementation | Evidence required to close |
|---|---|---|
| **M0 · Establish a reference build** | Select one exact Chipyard commit and qualify the existing complete-installation container (C0). Record its generator/submodule commits, JDK, sbt, Scala, Chisel, CIRCT and Verilator versions. Build a stock configuration using the upstream flow and run a small deterministic payload. | Commit a baseline recipe and the command, configuration, payload identity and expected pass result. Record the reference image identity and actual installed versions. This gives subsequent failures a known reference. Resolver development can proceed in parallel. |
| **M1 · Resolve a workspace** | Deliver A1, A2 and the graph/lock/cache portions of A4–A6. Support local sources, pinned Git sources, a Chipyard platform recipe and recipe-declared transitive dependencies. Accept aliases now. | From a clean workspace, resolve with no experiment selected. A second resolve yields the same lockfile. Resolve two aliases at different commits and inspect both nodes. Exercise duplicate aliases, incompatible shared dependencies, local edits, concurrent cache fills and an offline rerun after prefetch. A failed fetch leaves no usable partial entry. |
| **M2 · Build from outside Chipyard** | Implement the generated second build and the first experiment input task, provisionally `sbt "hardwareElaborate baseline"`. Reuse Chipyard elaboration and Verilator through the pinned recipe; qualify the complete-installation container path (C1–C4) alongside this milestone. | Reproduce M0's functional result using an external workspace. Then build two separate workspaces with the same plugin release, one consuming local generator source and one pinned Git source. Elaborate their actual contributions, delete generated directories and rebuild. No tool edits or manual Chipyard registration between runs. Show that local BOOM edits are reflected in elaboration without rebuilding the container or modifying the installed checkout. |
| **M3 · Select hardware and integrations** | Implement the typed standalone prototype and selected-system path. Add the import selector and emit the selected source list with reasons. Keep system choice out of the lockfile. | Standalone elaboration works without a system. Two experiments with the same qualified entry name compile independently. An intentionally broken optional adapter is harmless until imported. Test recursive helper imports, comments and strings, an imported but uninstantiated adapter, and a cached but undeclared host. Switch back to baseline with warm caches and verify its classpath and RTL. |
| **M4 · Select aliased revisions in separate experiments** | Preserve alias-facing typed imports for two compatible revisions. Prototype isolated compilation and an alias-aware namespace mapping. If generator-owned names need relocation, validate syntax-aware rewriting on derived sources. | Switch A → B → A by experiment alone. Verify the compiled and elaborated revision using a distinguishing observable in each fixture and confirm the graph and lockfile are identical. Repeat with warm caches and test on two compatible BOOM revisions. Check platform type identity and original source integrity. |
| **M5 · Validate the v1 tool boundary** | Build one workspace that instantiates a whole generator and one that replaces an internal component through a verified host hook. Use the BTB as the replacement fixture if the pinned host supports the required interface. Run the simulator through the same tool entry point. | Both workspaces run independently with the same packaged release. For the replacement, compare baseline and custom configurations on a functional payload and verify which implementation was instantiated. Record experiment, lock fingerprint, sources, parameters, toolchain, execution provenance and backend in each manifest. A missing hook produces a clear unsupported-integration result. |
| **M6 · Follow-on capabilities** | Add a separately distributed non-Chisel wrapper, prototype two compatible revisions in one SoC, and qualify additional backends individually. | For a wrapper, reproduce RTL production and simulate the whole component. For a mixed-revision SoC, verify distinct hart/configuration identities, collision-free RTL/resources and correct execution on both instances. Each backend must pass a representative workload before claiming support. |

M1 and M2 deliver the first usable build path. M3–M5 cover the design's v1 targets, including separate-experiment aliases and one genuine internal replacement. M6 can proceed as separate workstreams. C0–C4 below qualify the initial complete-installation container path; C5–C7 extend portability, cluster execution and backend coverage. The resolver work in M1 does not need to wait for container qualification. Container milestones supplement, rather than replace, the original milestones.

## Container integration strategy and milestones

### Execution model

The existing Dockerfile is assumed to install a complete Chipyard checkout and its toolchain. Presolve should adopt that installation as a platform provider, not reinstall Chipyard or require the Dockerfile to be split into a toolchain-only image. The installed Chipyard revision is the initial compatibility baseline. `build.sbt` and `hardware.lock` remain authoritative about the actual resolved inputs, and `System.scala` remains authoritative about the selected system. An installed generator is not automatically available to workspace code simply because it exists in the image.

```text
Existing Dockerfile / published OCI image
  -> Complete Chipyard installation + toolchain (protected)
       | inspect identity, initialize environment, reuse matching inputs
       v
Mounted user workspace: build.sbt, hardware.lock, config/, local sources
  -> Outer sbt load: Presolve plugin resolves dependencies and writes plan
  -> Inner sbt load: generated isolated writable build under target/hardware/
  -> Selected backend: elaborate, simulate, or deploy
  -> Artifacts, logs and run manifest
```

Start by launching sbt in the existing image and loading Presolve from the workspace's `project/plugins.sbt` (a published plugin or a mounted local artifact repository). Both sbt loads and platform-specific commands run in the same initialized environment. The host only needs a container launcher for this path. A native runner executes inside the container; host-side Docker/Apptainer orchestration is a later convenience, not a prerequisite. No Presolve image layer or container-in-container execution is required.

The installation descriptor should carry the Chipyard root, initialization command/script, platform identity, toolchain capabilities and any required path mappings. The exact interface and setting names are to be chosen after the reference installation is inspected. A versioned recipe must decide which build files, resources, generated inputs and source directories are needed, and whether they can be referenced directly or require a writable copy. Do not reuse precompiled Scala/native outputs unless their complete build fingerprint matches. If installed source provenance cannot be verified, treat it as ineligible for cache reuse; if the platform or required tools cannot be verified or are incompatible, fail qualification rather than silently using another version.

Use mountable host-owned workspaces and writable per-run output directories, with explicit cache locations for sbt/Coursier/Ivy and other tools where needed. Preserve path visibility for local generators, including external checkouts if explicitly declared. Avoid mounting over the installed Chipyard root or allowing the original tree to shadow selected sources. A local source edit should invalidate the affected build, not the image. A toolchain change may require a different image; a different generator revision does not, if it is compatible.

### Container milestones and exit tests

| Milestone | Integration with main plan | Implementation | Evidence required to close |
|---|---|---|---|
| **C0 · Qualify the existing full Chipyard image** | M0; parallel with M1 | Inspect the actual Dockerfile/image, entrypoint, user, Chipyard root, environment initialization, installed revisions (including submodules), tools, caches and absolute-path assumptions. Build or pull the existing image and pin its digest/architecture. Run the upstream reference configuration using the installed Chipyard flow; use a disposable container or isolated writable copy if upstream writes into its checkout. | Record a complete installation inventory, image identity, command, payload and functional pass result. Confirm which resources are relocatable, which require the installed path and which writes must be redirected. No new Presolve-specific Dockerfile is necessary for this gate. |
| **C1 · Run Presolve in the existing image** | M1–M2; after C0 | Mount a standard workspace, initialize the installed environment and load the pinned Presolve sbt plugin. Use a native execution runner within the container for both build loads. Configure writable artifact/cache locations, explicit local-source mounts and usable file ownership. | Resolve a local and a Git generator inside the unmodified image; produce a deterministic lock on repeat resolution and usable host-side outputs. Verify the host does not require an sbt/JDK installation and no nested container runtime is used. |
| **C2 · Adopt and validate installed platform inputs** | M1–M2; after C0, alongside C1 | Implement the installed-platform provider and recipe-based source lookup. Match installed Chipyard and generators against resolved immutable identities and source integrity. Prefer verified matching inputs, use explicit local/Git sources where selected, fetch missing compatible sources, and diagnose incompatible or unverifiable inputs. | Verify exact-match reuse without refetch; test a compatible differing revision and a deliberately incompatible toolchain/platform. A baked-in but undeclared generator remains unavailable. The selected local generator is the only compiled instance for its identity; demonstrate no implicit fallback. |
| **C3 · Build in a separate writable workspace** | M2; after C1–C2 | Generate the second sbt build under `target/hardware/`; reuse installed scripts/toolchain through the pinned recipe. Reference or copy only required inputs; handle environment setup, path mapping and resource layout. Run elaboration and Verilator without modifying the installed checkout. | Reproduce the C0/M0 reference payload with a generated external workspace. Verify installed sources and relevant infrastructure remain unchanged; test cold/warm runs, cleanup and regeneration. Confirm generated artifacts do not depend on unintended baked-in classpath entries. |
| **C4 · Validate local BOOM development and reproducible container builds** | M2; regress at M4–M5; after C3 | Exercise an existing BOOM fork kept under `development/boom/` and declared through `Generator.local()`. Keep a pinned upstream baseline as a distinct alias where needed. Add image identity and installed-source provenance to locks, fingerprints and manifests. | Build baseline and modified BOOM; change a known observable in local BOOM, rebuild and verify elaborated RTL/functional behavior changes without rebuilding the image or touching its installed BOOM. Verify a stale compiled artifact cannot hide the edit; reject image/toolchain drift in strict mode. Repeat from clean outputs with pinned inputs. |
| **C5 · Qualify Docker and Apptainer execution** | After C3–C4; can run alongside M3–M5 | Reuse the same published OCI image for Docker and for an Apptainer SIF. Implement common command-runner/path-mapping contracts and optional host-side launch adapters; support prebuilt images, then Dockerfile builds as a convenience. Provide documented manual launch commands regardless of automation. | Run the same pinned workspace and deterministic payload on both runtimes, including Apptainer with a read-only SIF and writable mounted outputs. Record OCI digest and SIF checksum; demonstrate usable file ownership, environment initialization, error propagation and no runtime-specific source edits. |
| **C6 · Qualify parallel execution on Slurm** | After C5; cluster workstream | Use per-job writable build/output directories and safe shared dependency/tool caches, with an isolated or read-only installed tree. Support explicit binds, scheduler-provided resources and execution without privileged Docker. | Run at least two simultaneous configurations from the same image and shared immutable sources. Verify independent results, cache integrity, no cross-job writes, correct resource/exit reporting and safe cancellation. Where offline execution is required, prefetch dependencies and demonstrate a repeat job without network access. |
| **C7 · Qualify FireSim/FPGA deployment** | M6; after C5, with C6 for cluster deployment | Reuse installed FireSim and compatible tools where available; qualify vendor tools, licenses, drivers/devices, FPGA platform and any additional writable state separately. Keep deployment/backend-specific commands out of the resolver. | Build a representative FPGA image and execute a known workload on the intended platform; record tool versions, bitstream identity, FPGA configuration, payload and results. Do not claim FireSim support based solely on Verilator success or the presence of FireSim in the image. |

C0–C4 are the minimum complete-installation container qualification path. C5 and C6 provide the Docker-to-Apptainer/Slurm workflow for large-scale experiments; C7 qualifies actual FPGA deployment. Native execution, a Presolve-inherited convenience image, overlays and more aggressive cache optimization may be supported independently; none is required to adopt the existing Dockerfile. An image that fails qualification must produce a documented incompatibility or narrowly scoped recipe adjustment, not silently switch to a different Chipyard installation.

## Decisions to make when evidence is available

| When | Decision | How to decide |
|---|---|---|
| M0 / C0 | Exact reference revision and configuration (Q-09, platform portion) | Pin the existing image and installed revision whose upstream build runs the reference payload. Record actual tool versions, installation root and initialization procedure. |
| C1–C3 | Installed platform descriptor, environment activation and writable layout | Test the actual Dockerfile and identify path/resource dependencies. Prefer read-only references and isolated outputs; copy only when required by the pinned recipe. |
| C2–C4 | Source provenance and image identity policy | Verify installed sources against resolved identities; use explicit local/Git inputs without fallback, reject incompatible tools, and verify repeatability after local edits. |
| C5–C6 | Runtime/mount contract, cache locations and Slurm execution | Qualify the same pinned image on Docker and Apptainer, including read-only SIF, external local-source paths and concurrent jobs. |
| C7 | FireSim/FPGA prerequisites and deployment contract | Verify the real target platform, tools, licenses, drivers/devices and a functional workload before claiming support. |
| M2–M3 | Final entry class discovery and standalone signature (Q-01–Q-05, Q-12) | Compile two unrelated workspaces, including one with a parameterized standalone module. Check that users never need to register experiments in the manifest. |
| M3 | Integration package mapping and supported named-import forms (Q-07, Q-19) | Exercise transitive unit selection, ambiguous symbols, missing prerequisites and cold/warm builds. Document the accepted syntax and diagnostics. |
| M4 | Alias namespace mechanism (Q-20–Q-21) | Accept the simplest implementation that preserves typed alias imports, correct shared types and reproducible revision selection. Directory suffixes alone establish source isolation only. |
| M5–M6 | Host hook and broader wrapper contracts (Q-09–Q-10, Q-13–Q-14) | Inspect the pinned implementation and verify behavior in simulation. Generalize only the lifecycle operations shared by the tested integrations. |

**First pull request.** Package the minimal plugin, expose `hardwareResolve`, evaluate declarations from two fixture workspaces, resolve local and pinned Git inputs, and write a deterministic lockfile. Reviewers should be able to copy either fixture outside the checkout, run resolution twice, and inspect why every graph node is present. This gives the second pull request a concrete build plan to consume.


**Container implementation sequence.** Qualify the existing image (C0) in parallel with resolver development. Integrate C1–C4 into the M2 build-path work rather than delaying container support until after v1. Keep the first resolver pull request focused as originally planned. C5–C7 can be separate pull requests with their own exit evidence.
