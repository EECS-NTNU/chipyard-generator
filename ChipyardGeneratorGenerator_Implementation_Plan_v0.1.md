# ChipyardGeneratorGenerator implementation plan

**Companion to design v0.12 · Plan v0.1 · 25 November 2026**

The first delivery is a released tool that two independent hardware workspaces can use. A researcher pins the plugin, declares generators in `build.sbt`, and builds from the workspace root. Chipyard is a pinned platform dependency. The BTB exercises one capability, internal component replacement. A small whole-generator example exercises the same tool through a different integration path.

The decisions below are implementation defaults for the first prototype. The milestones describe evidence to collect. No platform revision, host hook, or multi-version compilation strategy has yet passed these gates.

## Architectural decisions

| ID | Decision | Consequence for implementation |
|---|---|---|
| A1 | Release the plugin, resolver, workspace generator and Chipyard recipes from the tool repository. Keep hardware, experiment definitions, dependency declarations and the lockfile in the user's workspace. | Test workspaces consume a published or locally packaged plugin by version. They can live as fixtures during development, but must also build after being copied outside the tool checkout. The generated build directory is disposable. |
| A2 | Use an sbt plugin as the initial front end. Let sbt evaluate the workspace's settings. Implement resolution and build-plan generation as Scala code callable independently of an sbt session. | The first command is `sbt hardwareResolve`. A later CLI can call the same operations. There is one user-authored dependency declaration surface. |
| A3 | Start with two build loads. The outer build resolves and writes a plan. A separate, generated sbt build compiles the resolved projects and selected sources. | This puts dependency discovery before construction of the compilation graph. The generated build uses the pinned Chipyard recipe and cannot recursively invoke the outer resolve task. Revisit native sbt project references only if they preserve this boundary and simplify the implementation. |
| A4 | Resolve once per workspace. Represent each generator instance by its declared identity, optional alias, resolved source and explicit dependency edges. | Preserve distinct revisions and share compatible platform nodes. Validate alias uniqueness and report both dependency paths on a platform conflict. An experiment selects from this graph. |
| A5 | Use a schema-versioned, deterministically ordered `hardware.lock`. Record roots, nodes, edges, revisions, submodule pins, recipes, toolchain and local source identities. | First resolve writes the lock. An ordinary build verifies it and reports drift. An explicit resolve updates it after a declaration or local dependency changes. Record workspace-relative local paths where possible and fingerprint their build inputs. Keep the experiment choice and run parameters in a separate run manifest. |
| A6 | Cache fetched sources by canonical repository and commit. Generate build files under the workspace's `target/hardware/`. | Publish complete cache entries atomically. Concurrent jobs use isolated writable build directories. Fingerprint compiled artifacts with the actual toolchain, recipes, dependency edges, selected sources and any alias transformation. |
| A7 | Use one Chipyard `Config` entry per selected `config/<experiment>/System.scala` for the first system build. Prototype a workspace-package convention with a class named `System`. | The build manager explicitly selects the experiment directory and passes its qualified entry class to elaboration. A baseline can omit the local hardware. Test the convention before publishing it as an API. |
| A8 | Start standalone support with one public `object Module` in the canonical `Module.scala`, a typed `create(params)` factory and workspace-supplied default parameters. | Generate a small compile-time-checked driver for a directly elaboratable Chisel module. Each call constructs fresh hardware. Validate the package/symbol convention with a second workspace before fixing the public signature. Diplomacy and external RTL may require different construction contexts. |
| A9 | Select optional integrations from named Scala imports before compilation. Resolve dependency aliases independently of this source-selection step. | Index exported integration packages or symbols by source unit. Traverse imports in active sources, including helpers and newly selected units, to a fixed point. Only resolved dependencies are eligible. Expose selected units and reasons in the build plan. |
| A10 | Keep platform- and host-specific knowledge in versioned recipes and adapters. The core tool handles source identities, build inputs, compilation and backend invocation. | A recipe identifies source/resource roots, compiler settings, project edges and required build steps. A workspace explicitly opts into an external build recipe before its commands run. A host-specific adapter owns the semantics of a replacement. |

## Milestones and exit tests

| Milestone | Implementation | Evidence required to close |
|---|---|---|
| **M0 · Establish a reference build** | Select one exact Chipyard commit. Record its generator/submodule commits, JDK, sbt, Scala, Chisel, CIRCT and Verilator versions. Build a stock configuration using the upstream flow and run a small deterministic payload. | Commit a baseline recipe and the command, configuration, payload identity and expected pass result. This gives subsequent failures a known reference. Resolver development can proceed in parallel. |
| **M1 · Resolve a workspace** | Deliver A1, A2 and the graph/lock/cache portions of A4–A6. Support local sources, pinned Git sources, a Chipyard platform recipe and recipe-declared transitive dependencies. Accept aliases now. | From a clean workspace, resolve with no experiment selected. A second resolve yields the same lockfile. Resolve two aliases at different commits and inspect both nodes. Exercise duplicate aliases, incompatible shared dependencies, local edits, concurrent cache fills and an offline rerun after prefetch. A failed fetch leaves no usable partial entry. |
| **M2 · Build from outside Chipyard** | Implement the generated second build and the first experiment input task, provisionally `sbt "hardwareElaborate baseline"`. Reuse Chipyard elaboration and Verilator through the pinned recipe. | Reproduce M0's functional result using an external workspace. Then build two separate workspaces with the same plugin release, one consuming local generator source and one pinned Git source. Elaborate their actual contributions, delete generated directories and rebuild. No tool edits or manual Chipyard registration between runs. |
| **M3 · Select hardware and integrations** | Implement the typed standalone prototype and selected-system path. Add the import selector and emit the selected source list with reasons. Keep system choice out of the lockfile. | Standalone elaboration works without a system. Two experiments with the same qualified entry name compile independently. An intentionally broken optional adapter is harmless until imported. Test recursive helper imports, comments and strings, an imported but uninstantiated adapter, and a cached but undeclared host. Switch back to baseline with warm caches and verify its classpath and RTL. |
| **M4 · Select aliased revisions in separate experiments** | Preserve alias-facing typed imports for two compatible revisions. Prototype isolated compilation and an alias-aware namespace mapping. If generator-owned names need relocation, validate syntax-aware rewriting on derived sources. | Switch A → B → A by experiment alone. Verify the compiled and elaborated revision using a distinguishing observable in each fixture and confirm the graph and lockfile are identical. Repeat with warm caches and test on two compatible BOOM revisions. Check platform type identity and original source integrity. |
| **M5 · Validate the v1 tool boundary** | Build one workspace that instantiates a whole generator and one that replaces an internal component through a verified host hook. Use the BTB as the replacement fixture if the pinned host supports the required interface. Run the simulator through the same tool entry point. | Both workspaces run independently with the same packaged release. For the replacement, compare baseline and custom configurations on a functional payload and verify which implementation was instantiated. Record experiment, lock fingerprint, sources, parameters, toolchain and backend in each manifest. A missing hook produces a clear unsupported-integration result. |
| **M6 · Follow-on capabilities** | Add a separately distributed non-Chisel wrapper, prototype two compatible revisions in one SoC, and qualify additional backends individually. | For a wrapper, reproduce RTL production and simulate the whole component. For a mixed-revision SoC, verify distinct hart/configuration identities, collision-free RTL/resources and correct execution on both instances. Each backend must pass a representative workload before claiming support. |

M1 and M2 deliver the first usable build path. M3–M5 cover the design's v1 targets, including separate-experiment aliases and one genuine internal replacement. M6 can proceed as separate workstreams.

## Decisions to make when evidence is available

| When | Decision | How to decide |
|---|---|---|
| M0 | Exact reference revision and configuration (Q-09, platform portion) | Pin a revision whose documented upstream build runs the reference payload on the development machine or cluster. Record the actual versions from that run. |
| M2–M3 | Final entry class discovery and standalone signature (Q-01–Q-05, Q-12) | Compile two unrelated workspaces, including one with a parameterized standalone module. Check that users never need to register experiments in the manifest. |
| M3 | Integration package mapping and supported named-import forms (Q-07, Q-19) | Exercise transitive unit selection, ambiguous symbols, missing prerequisites and cold/warm builds. Document the accepted syntax and diagnostics. |
| M4 | Alias namespace mechanism (Q-20–Q-21) | Accept the simplest implementation that preserves typed alias imports, correct shared types and reproducible revision selection. Directory suffixes alone establish source isolation only. |
| M5–M6 | Host hook and broader wrapper contracts (Q-09–Q-10, Q-13–Q-14) | Inspect the pinned implementation and verify behavior in simulation. Generalize only the lifecycle operations shared by the tested integrations. |

**First pull request.** Package the minimal plugin, expose `hardwareResolve`, evaluate declarations from two fixture workspaces, resolve local and pinned Git inputs, and write a deterministic lockfile. Reviewers should be able to copy either fixture outside the checkout, run resolution twice, and inspect why every graph node is present. This gives the second pull request a concrete build plan to consume.
